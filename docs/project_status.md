# Текущее состояние проекта NoteVision OMR

## 1. Цель проекта

NoteVision OMR — система анализа сканированных нотных документов Российской
государственной библиотеки. Цель проекта состоит в построении
воспроизводимого конвейера, который принимает исходные PDF-документы и
библиографические записи MRC, определяет страницы с нотной записью,
подготавливает их для оптического распознавания музыки и формирует результаты
в формате MusicXML/MXL.

Целевой процесс обработки:

`PDF/MRC → страницы → детекция нотных страниц → ручная валидация → OMR → MXL → музыкальные признаки и MIDI`

## 2. Структура pipeline

### 2.1. Импорт PDF и MRC

Скачанные файлы помещаются в общую папку `data/inbox/`. Скрипт импорта
сопоставляет PDF и MRC по идентификатору РГБ, после чего создаёт
структурированные каталоги `data/raw/<doc_id>/`. Исходные имена файлов
сохраняются, а в каждой папке документа создаётся файл `source.txt` с
информацией о происхождении данных.

### 2.2. Извлечение страниц

PDF преобразуется в набор PNG-изображений. Для каждой страницы сохраняются
номер, размер, разрешение и путь к изображению. Основной pipeline использует
каталог `outputs/pages/<doc_id>/` и файл `manifest.csv`.

### 2.3. Парсинг MRC

Библиографические записи читаются через `pymarc`. Из MRC извлекаются название,
авторы, год, язык, сведения об издании, физическое описание, предметные
рубрики, идентификатор записи и электронные ресурсы. Результаты сохраняются в
JSON и могут объединяться в общий CSV.

### 2.4. Детекция нотных страниц

Baseline-детектор анализирует бинаризованные изображения и выделяет
горизонтальные линии с помощью морфологических операций OpenCV. Решение о
наличии нотной записи основано на числе линий, их плотности и количестве групп,
похожих на нотные станы.

### 2.5. Ручная валидация

Автоматические прогнозы преобразуются в шаблон разметки. Для визуальной
проверки формируется HTML-галерея с изображениями страниц, предсказаниями,
оценками уверенности и ручными метками. Валидированная разметка используется
для расчёта итоговых метрик детектора и выбора страниц для OMR.

### 2.6. Формирование OMR candidates

В список кандидатов включаются только страницы, для которых одновременно
выполняются условия `has_music == 1` и `page_type == "music"`. Для каждой
страницы указываются исходное изображение, путь к предобработанной версии,
комментарий о качестве и наличие файла.

### 2.7. Извлечение OMR-страниц в 300 DPI

Для OMR-кандидатов страницы повторно извлекаются непосредственно из исходных
PDF при разрешении 300 DPI. Они сохраняются отдельно в
`outputs/omr_pages/<doc_id>/` и не заменяют изображения основного pipeline в
`outputs/pages/`.

### 2.8. Audiveris OMR

Предобработанные или повторно извлечённые страницы передаются во внешний
инструмент Audiveris через CLI. Для каждой страницы создаётся отдельный каталог
результатов, сохраняются журналы stdout/stderr, внутренний проект Audiveris и
экспорт MXL. Ошибка одной страницы не останавливает пакетную обработку.

### 2.9. Сводка OMR-результатов

Финальный этап объединяет статусы запусков Audiveris, подсчитывает долю
успешных обработок, находит созданные `.mxl`-файлы и рассчитывает статистику их
размеров. В отчёт также входят списки успешных и неуспешных страниц.

Матрица ошибок:

|  | Предсказано: без нот | Предсказано: ноты |

улучшения — снижение числа false positive.

## 5. OMR-эксперимент

### 5.1. Эксперимент при 200 DPI

Первая серия была выполнена на десяти OMR-кандидатах:

- успешно обработано: 6 страниц;
- завершилось ошибкой: 4 страницы;
- success rate: 60%.

В журналах Audiveris причиной ошибок указывалось слишком малое значение
`interline`. Это означает, что расстояние между линиями нотного стана на
изображении оказалось недостаточным для устойчивой работы алгоритмов
Audiveris.

### 5.2. Эксперимент при 300 DPI

После повторного извлечения страниц при повышенном разрешении проведена серия
на 50 кандидатах:

- успешно обработано: 50 страниц;
- завершилось ошибкой: 0 страниц;
- success rate: 100%.

Всего сформирован 51 файл MXL. Различие между числом страниц последней серии и
общим числом MXL связано с накопленными результатами экспериментальных
запусков.

Результат показывает, что разрешение исходного изображения является
существенным фактором технической устойчивости OMR.

## 6. Анализ ошибок

В ходе ручной проверки выявлено, что часть пустых страниц была ошибочно
классифицирована как содержащая нотную запись. Причиной стали визуальные
структуры, которые baseline-алгоритм интерпретировал как горизонтальные линии
нотного стана.

После визуальной проверки исправлена разметка следующих страниц документа
`rsl01001872102`:

- `page_003`;
- `page_004`;
- `page_059`–`page_063`.

Эксперименты Audiveris также показали высокую чувствительность OMR к DPI.
Страницы, не прошедшие обработку при 200 DPI из-за малого `interline`, были
успешно обработаны после повторного извлечения при 300 DPI.

## 7. Ограничения

- Разметка страниц частично выполнена вручную и пока охватывает ограниченное
  число документов.
- Наличие MXL-файла подтверждает техническое завершение OMR, но не гарантирует
  музыкальную корректность распознанных нот, ритма, голосов и структуры
  партитуры.
- Качество MXL пока проверено преимущественно технически, без полной
  музыкальной экспертной оценки.
- Audiveris является внешним инструментом, поэтому воспроизводимость зависит
  от его версии, конфигурации и доступности среды Java.
- Требуется отдельная методика количественной оценки качества распознавания
  нотных символов и музыкальной структуры.

## 8. Следующие шаги

1. Открыть выборку MXL-файлов в MuseScore и провести визуальную проверку
   нотного текста.
2. Реализовать преобразование MusicXML/MXL в MIDI и проверить корректность
   воспроизведения.
3. Расширить ручную валидацию страниц и число обрабатываемых документов.
4. Добавить показатели качества OMR-результатов, включая ошибки высоты,
   длительности, тактовой структуры и количества голосов.
5. Сопоставить качество результатов с параметрами исходных изображений и
   определить рекомендуемые настройки извлечения и предобработки.

## Итог

На текущем этапе реализован полный экспериментальный pipeline от импорта
исходных PDF/MRC до получения MXL и сводного отчёта. Детектор нотных страниц
демонстрирует высокий recall, а переход от 200 к 300 DPI существенно повысил
устойчивость Audiveris. Следующий этап работы должен перейти от проверки
технического факта создания MXL к оценке музыкальной корректности результата.
