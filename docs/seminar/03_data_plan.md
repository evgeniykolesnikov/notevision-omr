# Задание 3. Методы работы с данными

## Проект

**NoteVision OMR — анализ сканированных нотных документов РГБ**

## 1. Цель работы с данными

Данные являются основой всех этапов NoteVision OMR. Система последовательно
преобразует исходные библиотечные материалы в набор промежуточных и итоговых
артефактов:

`PDF/MRC → страницы → labels → OMR candidates → MXL → MIDI`

PDF содержит визуальное представление документа, MRC/MARC — библиографические
метаданные. После извлечения страниц формируется разметка наличия нотной записи,
на её основе выбираются кандидаты для OMR, а результаты Audiveris
преобразуются из MXL в MIDI. Цель работы с данными в MVP — обеспечить
воспроизводимое прохождение этого пути с сохранением происхождения файлов,
статусов обработки и ошибок каждого этапа.

## 2. Источники данных

Исходный корпус состоит из PDF-сканов нотных документов и соответствующих
библиографических записей MRC/MARC. На текущем этапе обработано 6 документов,
включающих 434 страницы.

Исходники хранятся локально в каталогах `data/raw/<doc_id>/`. Реальные PDF и
MRC не коммитятся в Git: репозиторий содержит код, документацию и пустую
структуру каталогов, но не библиотечные материалы.

| Тип данных | Назначение | Пример пути | Статус в MVP |
|---|---|---|---|
| PDF | Источник сканированных страниц документа | `data/raw/rsl01004470876/rsl01004470876.pdf` | Используется |
| MRC/MARC | Библиографическое описание документа | `data/raw/rsl01004470876/01004470876.mrc` | Используется при наличии |
| `source.txt` | Фиксация идентификатора и происхождения локального импорта | `data/raw/rsl01004470876/source.txt` | Формируется при импорте |
| PNG 200 DPI | Страницы для baseline-детектора и ручной проверки | `outputs/pages/rsl01004470876/page_001.png` | Формируется |
| PNG 300 DPI | Страницы-кандидаты для Audiveris | `outputs/omr_pages/rsl01004470876/page_001.png` | Формируется |
| CSV-разметка | Ground truth и результаты ручной проверки | `data/labels/pages_validated.csv` | Используется |
| MXL | Машиночитаемый результат OMR | `outputs/omr_300dpi/<doc_id>/page_XXX/page_XXX.mxl` | Получен на экспериментальном срезе |
| MIDI | Производное представление для музыкального ПО | `outputs/midi/<doc_id>/page_XXX.mid` | Получено на тестовом batch-срезе |

## 3. Организация данных

Данные разделены по этапам жизненного цикла:

```text
data/inbox/                       # общая папка для скачанных PDF и MRC
data/raw/<doc_id>/                # структурированные неизменённые исходники
outputs/pages/<doc_id>/           # страницы основного pipeline, 200 DPI
outputs/preprocessed/<doc_id>/    # бинаризованные нотные страницы
outputs/omr_pages/<doc_id>/       # повторно извлечённые OMR-страницы, 300 DPI
outputs/omr_300dpi/<doc_id>/      # результаты Audiveris, включая MXL
outputs/midi/<doc_id>/            # MIDI-файлы
outputs/reports/                  # CSV-, JSON- и HTML-отчёты
```

Каталоги `outputs/` содержат воспроизводимые производные данные и не
коммитятся в Git. В репозитории сохраняются только файлы `.gitkeep`,
поддерживающие структуру пустых каталогов.

## 4. Сбор и импорт

Пользователь загружает PDF-сканы и MRC-файлы в общую папку `data/inbox/`.
Скрипт `scripts/organize_raw_files.py` определяет `doc_id` по имени файла,
группирует связанные материалы и копирует либо перемещает их в
`data/raw/<doc_id>/`, не изменяя исходные имена.

Для каждого документа создаётся `source.txt`, в котором фиксируются `doc_id`,
источник импорта, дата и поле для примечаний. Общий
`outputs/reports/raw_import_report.csv` содержит исходный и целевой пути,
тип файла, статус операции и сообщение. Наличие только PDF или только MRC
считается предупреждением, а не аварийной ошибкой импорта.

## 5. Извлечение страниц

Скрипт `scripts/extract_pages.py` открывает PDF через PyMuPDF и сохраняет
каждую страницу как `page_XXX.png`. Основной pipeline использует разрешение
200 DPI: этого достаточно для первичного анализа, расчёта CV-признаков и
ручной проверки разметки.

В каталоге каждой выгрузки создаётся `manifest.csv` с полями `doc_id`,
`page_index`, `image_path`, `width`, `height` и `dpi`. Manifest связывает
страницу с исходным документом и используется последующими этапами.

Для Audiveris применяется отдельное повторное извлечение выбранных страниц при
300 DPI через `scripts/extract_omr_pages.py`. Эти изображения сохраняются в
`outputs/omr_pages/` и не заменяют страницы основного pipeline в
`outputs/pages/`.

## 6. Метаданные

Скрипт `scripts/parse_mrc.py` читает MRC/MARC через `pymarc` и извлекает:

- `title`;
- `authors`;
- `year`;
- `language`;
- `publication`;
- `physical_description`;
- `record_id`;
- `electronic_resources`.

Парсер допускает неполные записи и возвращает пустые значения вместо остановки
pipeline. Метаданные сохраняются в JSON или объединённом CSV. В MVP они
используются в отчётах; в дальнейшем могут поддерживать поиск, фильтрацию,
каталогизацию и связывание распознанного музыкального материала с
библиографическим описанием.

## 7. Разметка

Файл `pages_template.csv` создаётся автоматически на основе прогнозов
music-page detector. После визуальной проверки формируется
`pages_validated.csv`, содержащий ручную или частично ручную корректировку.

Основные поля разметки:

| Поле | Назначение |
|---|---|
| `doc_id` | Идентификатор документа |
| `page_index` | Номер страницы, начиная с 1 |
| `page_type` | Тип содержимого страницы |
| `has_music` | Валидированная бинарная метка наличия нот |
| `quality_comment` | Комментарий оператора о качестве или содержимом |
| `image_path` | Путь к изображению страницы |
| `has_music_pred` | Прогноз baseline-детектора |
| `has_music_score` | Rule-based оценка уверенности |

Используемые значения `page_type`:

- `music` — страница с нотной записью;
- `title` — титульная или выходная страница;
- `text` — преимущественно текстовая страница;
- `blank` — пустая или практически пустая страница;
- `unknown` — тип не определён или требует проверки.

При ручной валидации были исправлены пустые страницы, ошибочно отмеченные как
нотные:

- `rsl01001872102/page_003`;
- `rsl01001872102/page_004`;
- `rsl01001872102/page_059`–`page_063`.

Эта корректировка показывает, что rule-based признаки горизонтальных линий
могут давать false positive на артефактах сканирования и пустых листах.

## 8. Предобработка

Скрипт `scripts/preprocess_music_pages.py` выбирает только строки с
`has_music == 1`. Для каждой страницы выполняются чтение изображения,
преобразование в оттенки серого, нормализация контраста и бинаризация.
Результаты сохраняются как
`outputs/preprocessed/<doc_id>/page_XXX_binary.png`.

После ручной корректировки подготовлено 392 preprocessed-файла. Статус каждой
операции записывается в `outputs/reports/preprocessing_report.csv`. Ошибка
одной страницы не останавливает пакетную обработку остальных данных.

## 9. Формирование OMR-кандидатов

Скрипт `scripts/build_omr_candidates.py` включает в список только строки,
одновременно удовлетворяющие условиям:

```text
has_music == 1
page_type == "music"
```

После ручной корректировки сформировано 392 OMR-кандидата. Для каждого
кандидата хранится путь `preprocessed_path`, а поле `exists` показывает,
существует ли соответствующий предобработанный файл. Список кандидатов
используется как контролируемый вход для повторного извлечения при 300 DPI и
запуска Audiveris.

## 10. Разбиение данных

В текущем MVP не обучается нейросетевая модель, поэтому классическое разбиение
на train, validation и test не выполнялось. Rule-based baseline оценивается на
всех 434 размеченных страницах после ручной валидации.

Такой расчёт подходит для проверки текущего конвейера, но не является оценкой
обобщающей способности обучаемой модели. Для ВКР потребуется:

- сформировать независимые train/validation/test-части;
- выполнять разбиение на уровне документов, а не отдельных страниц;
- не допускать попадания страниц одного документа одновременно в train и test;
- по возможности учитывать тип издания, период, качество скана и сложность
  нотной структуры.

Document-level split необходим, поскольку соседние страницы одного PDF имеют
схожие макет, качество печати и артефакты сканирования. Их смешивание между
train и test привело бы к утечке данных и завышенной оценке качества.

## 11. Аугментация

В MVP аугментации для обучения не используются, поскольку detector основан на
правилах и морфологических признаках OpenCV.

Для будущей нейросетевой модели могут применяться:

- небольшое размытие;
- изменение контраста и яркости;
- малые повороты;
- перспективные искажения;
- шум, имитирующий дефекты скана.

Параметры преобразований должны сохранять читаемость нотных станов и символов.
Вертикальный flip использовать нельзя: такое преобразование нефизично для
нотной страницы, меняет музыкальную геометрию и создаёт нереалистичные
обучающие примеры.

## 12. Контроль качества данных

| Проблема | Как обнаруживается | Как исправляется | Статус |
|---|---|---|---|
| Пустые страницы ошибочно определяются как `music` | Просмотр HTML-галереи, сравнение `has_music_pred` с ручной меткой | Установка `has_music = 0`, `page_type = "blank"` | Обнаружено и исправлено для 7 страниц |
| Текстовые и титульные страницы попадают в кандидаты | Ручная проверка `page_type`, анализ false positive | Присвоение `text` или `title`, исключение из candidates | Поддерживается разметкой |
| Недостаточное разрешение изображения | Ошибки Audiveris и сообщения о малом `interline` | Повторное извлечение выбранных страниц при 300 DPI | Реализовано; проверено на 50 кандидатах |
| Некорректная или неполная MRC-запись | Исключение парсера, пустые поля, batch error report | Безопасный разбор отсутствующих полей, фиксация ошибки по документу | Реализовано |
| Отсутствующий PDF или MRC | Поиск файла в `data/raw/<doc_id>/`, отчёт импорта или batch pipeline | PDF: документ пропускается с ошибкой; MRC: warning, PDF pipeline продолжается | Реализовано |
| Ошибка OMR отдельной страницы | Код возврата Audiveris, stdout/stderr и `omr_report.csv` | Ошибка изолируется; анализируется DPI и лог; остальные страницы продолжают обрабатываться | Реализовано |
| Некорректные повторы при MXL→MIDI | `repeat.ExpanderException` в `music21` | Повторная конвертация без repeat-barline и `RepeatExpression`, затем плоский fallback | Реализовано |
| Технически корректный, но музыкально неточный MXL | Открытие в MuseScore и экспертное сравнение со сканом | Ручная оценка нот, ритма, голосов и структуры | Требуется расширить в ВКР |

## 13. Этика и закон

В проекте не обрабатываются персональные данные. Исходные PDF и MRC не
публикуются в репозитории: `.gitignore` исключает `data/raw`, `data/inbox` и
производные каталоги `outputs`, оставляя только `.gitkeep`.

Доступность документа в цифровой библиотеке не означает автоматически
разрешение на массовое копирование, переработку или публикацию производных
наборов. При расширении корпуса необходимо отдельно проверить правовой режим
материалов РГБ, условия доступа и допустимые способы использования.

Производные MXL и MIDI также не должны публиковаться без проверки прав на
исходные произведения, конкретные издания и цифровые копии. В MVP данные и
результаты используются локально в учебно-исследовательских целях.

## 14. Метрики текущего набора данных

| Показатель | Фактическое значение |
|---|---:|
| Документы | 6 |
| Страницы | 434 |
| OMR-кандидаты после ручной корректировки | 392 |
| Accuracy music-page detector | 0.9816 |
| Precision music-page detector | 0.9800 |
| Recall music-page detector | 1.0000 |
| F1 music-page detector | 0.9899 |
| OMR при 300 DPI на 50 кандидатах | 50 success / 0 failed |
| MXL→MIDI batch | 10 success / 0 failed |

Метрики детектора характеризуют текущую валидированную выборку. Результат OMR
показывает техническую успешность запуска Audiveris и создания файлов, но не
доказывает музыкальную точность распознавания. Аналогично, успешная конвертация
MXL в MIDI означает отсутствие технической ошибки, а не полное совпадение с
оригинальной партитурой.

## 15. Ограничения данных

- Корпус мал: 6 документов и 434 страницы недостаточны для вывода о качестве
  на всём фонде нотных изданий РГБ.
- Разметка выполнена частично вручную и пока не проходила независимую
  экспертную проверку несколькими разметчиками.
- Отсутствует нотная ground truth на уровне символов, тактов, голосов, высот и
  длительностей.
- Технический статус `success` для MXL не равен музыкальной корректности
  результата.
- Тестовый набор может быть нерепрезентативен по историческим периодам,
  издательствам, типам печати, составу партитуры и качеству сканирования.
- В текущей оценке baseline нет независимого document-level test set.

Эти ограничения допустимы для демонстрации MVP, но должны учитываться при
интерпретации метрик и планировании ВКР.

## 16. Вывод

Текущие данные подготовлены в объёме, достаточном для MVP и демонстрации
сквозного pipeline проектного семинара: исходники организованы, страницы
извлечены и размечены, сформированы OMR-кандидаты, проверена обработка при
300 DPI и выполнена тестовая конвертация MXL в MIDI.

Для развития проекта в рамках ВКР необходимо расширить и разнообразить корпус,
формализовать экспертную оценку музыкальной точности, подготовить нотную ground
truth и внедрить document-level train/validation/test-разбиение для будущих
ML-моделей. Отдельной задачей остаётся правовая проверка возможности
масштабирования и публикации производных данных.
