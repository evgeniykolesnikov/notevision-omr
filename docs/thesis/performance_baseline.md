# Baseline производительности OMR pipeline

## 1. Цель измерения

Цель baseline — зафиксировать фактическую скорость текущего этапа Audiveris OMR и оценить порядок времени при масштабировании корпуса.

Измерение отвечает на вопросы:

- сколько времени Audiveris обрабатывает одну страницу;
- насколько различается время successful и failed страниц;
- есть ли длинные выбросы;
- сколько займёт OMR при разных размерах фонда и числе workers;
- какие части pipeline ограничены CPU, а какие — вводом-выводом.

Baseline не является benchmark всей цепочки PDF → MIDI. Текущие логи позволяют надёжно измерить внутренний проход Audiveris, но пока не содержат единого wall-clock таймера для извлечения PDF, detector, подготовки 300 DPI и MIDI-конвертации.

## 2. Методика

Источник данных:

- `outputs/reports/omr_report.csv`;
- нативные логи Audiveris в `outputs/omr_300dpi/<doc_id>/page_XXX/`;
- `data/labels/pages_validated_thesis.csv` для оценки числа OMR-страниц на документ.

Профилировщик:

```text
python scripts/profile_omr_runtime.py
```

Формируемые отчёты:

- `outputs/reports/omr_runtime_pages.csv`;
- `outputs/reports/omr_runtime_summary.csv`;
- `outputs/reports/omr_runtime_estimates.csv`.

Для каждой строки `omr_report.csv` выбирается последний нативный лог Audiveris. Длительность рассчитывается как разница между первой и последней временной меткой этого лога:

```text
duration_seconds = last_log_timestamp - first_log_timestamp
```

Статус `success` или `failed` берётся из `omr_report.csv`. Wrapper-логи `*_audiveris.log` не используются для определения времени.

### Ограничения измерения

- измеряется время внутри Audiveris, а не полное время запуска subprocess;
- не учитываются извлечение страницы в 300 DPI и конвертация MXL → MIDI;
- запуск выполнялся последовательно, поэтому baseline не показывает реальную эффективность нескольких workers;
- текущие артефакты не фиксируют точную модель CPU, объём RAM, версию JVM и версию Audiveris в отдельном manifest;
- выборка содержит 150 OMR-кандидатов и не представляет всё разнообразие фонда из 87963 документов;
- failed страницы могут завершаться до прохождения всех этапов, поэтому их среднее время нельзя интерпретировать как стоимость успешного OMR.

Для итогового эксперимента ВКР следует сохранять hardware/software manifest вместе с runtime CSV.

## 5. Оценка масштабирования

Расчёт:

```text
estimated_pages = documents × 51,561

estimated_time =
    estimated_pages × 15,765 seconds / workers
```

Предполагается:

- постоянная доля OMR-кандидатов;
- одинаковое распределение сложности страниц;
- непрерывная работа workers;
- идеальное линейное ускорение;
- отсутствие очередей, повторных запусков, downtime и конкуренции за ресурсы.

## 6. CPU-bound этапы

### Audiveris

Основной CPU-bound этап:

- поиск нотных станов и геометрии;
- распознавание символов;
- построение связей;
- анализ ритма, голосов и тактов;
- формирование структуры MusicXML.

Audiveris также использует память JVM и пишет `.omr`, логи и MXL, но вычисления являются главным ограничением.

### Detector музыкальных страниц

OpenCV выполняет:

- grayscale;
- Otsu threshold;
- морфологические операции;
- подсчёт горизонтальных линий.

Это CPU- и memory-bandwidth-bound обработка. Она значительно дешевле OMR и подходит как quick filter.

### Предобработка

CLAHE, бинаризация и преобразование изображений выполняются на CPU. Нагрузка хорошо распараллеливается по страницам, если диск успевает читать и записывать PNG.

### MXL → MIDI

Парсинг MusicXML, разворачивание repeat и построение потока `music21` используют CPU, но для текущего pipeline обычно должны быть дешевле Audiveris. Сложные партитуры и fallback могут увеличивать время.

## 7. IO-bound этапы

### Чтение PDF и запись PNG

Извлечение страниц сочетает:

- чтение PDF;
- CPU-rendering страницы;
- сжатие и запись PNG.

На быстром локальном SSD этап может быть ограничен rendering и compression; на сетевом хранилище — вводом-выводом.

### Работа с изображениями

Загрузка исходных PNG и запись 200/300 DPI копий создают большой последовательный поток данных. При нескольких workers диск или сетевое хранилище может стать общим bottleneck.

### Артефакты Audiveris

Каждый запуск создаёт:

- нативный лог;
- wrapper log;
- `.omr`;
- один или несколько `.mxl`.

Запись этих файлов является IO-bound частью OMR. Большое число мелких директорий также усложняет операции файловой системы.

### CSV/JSON-отчёты

Отчёты IO-bound, но их стоимость мала относительно изображений и Audiveris.

## 8. Потенциал ускорения

### 8.1. Не запускать OMR для неподходящих страниц

Наиболее дешёвое ускорение:

- quick detector на уменьшенном изображении или 200 DPI;
- OMR только для `has_music=1`;
- приоритет `page_type=music` и `mixed`;
- исключение `blank`, `text`, `title`, `bad_scan`;
- ручная проверка uncertain страниц до Audiveris.

Снижение числа OMR-кандидатов линейно уменьшает вычислительное время.

### 8.2. Skip-existing и resume

Перед запуском необходимо проверять:

- наличие MXL;
- checksum входной страницы;
- версию Audiveris;
- параметры DPI и конфигурации;
- статус предыдущей задачи.

Повторная обработка неизменившейся успешной страницы не должна выполняться.

### 8.3. Ограниченный параллелизм

Страницы независимы и могут обрабатываться разными workers. Однако ускорение до 2/4/8 workers нужно измерить, а не принимать равным числу процессов.

Ограничения:

- физические CPU cores;
- Java heap каждого процесса;
- конкуренция за память;
- чтение 300 DPI PNG;
- запись `.omr` и MXL;
- thermal throttling.

Практический benchmark должен отдельно запускать одну и ту же фиксированную выборку с 1, 2, 4 и 8 workers и измерять:

- wall-clock batch time;
- pages/hour;
- CPU utilization;
- peak RAM;
- failure rate;
- parallel efficiency.

### 8.4. Сократить startup overhead

Текущий runner запускает отдельный процесс Audiveris для каждой страницы. Возможное улучшение — передавать несколько страниц одному batch-запуску Audiveris, чтобы сократить startup JVM.

Компромисс:

- меньше startup overhead;
- хуже изоляция ошибки отдельной страницы;
- сложнее resume и сопоставление логов.

Следует сравнить single-page jobs и небольшие партии, например по 5–20 страниц.

### 8.5. Кэшировать извлечённые страницы

300 DPI PNG следует пересоздавать только при изменении:

- исходного PDF;
- номера страницы;
- DPI;
- параметров rendering.

Checksum и manifest предотвращают повторное чтение и rendering PDF.

### 8.6. Раннее выявление технически непригодных страниц

Failed страницы с длительностью менее двух секунд показывают, что часть ошибок выявляется рано. До Audiveris можно проверять:

- фактический размер изображения;
- interline estimate;
- наличие достаточного числа staff-like groups;
- сильную обрезку;
- color patch;
- пустое изображение;
- поворот и геометрическое искажение.

Такие страницы следует отправлять на preprocessing или ручную проверку, а не многократно перезапускать без изменения входа.

### 8.7. Профилировать внутренние шаги Audiveris

Нативные логи содержат переходы `LOAD`, `BINARY`, `SCALE`, `GRID`, `STEM`, `RHYTHMS`, `PAGE` и другие этапы. Следующее расширение профилировщика может рассчитывать время каждого шага и связывать выбросы с типом страницы.

Это особенно важно для `rsl01004475471/page_003`, время которой более чем в четыре раза превышает текущий p95.

### 8.8. Разделить лёгкие и тяжёлые очереди

Рекомендуется использовать отдельные worker pools:

- PDF/page extraction;
- detector/preprocessing;
- Audiveris;
- MIDI conversion;
- reports/export.

Audiveris pool ограничивается CPU и памятью, а лёгкие задачи не ждут завершения длинных OMR-страниц.

## 9. Рекомендации для следующего benchmark

1. Зафиксировать CPU, physical/logical cores, RAM, storage, Windows, Java и Audiveris.
2. Использовать неизменяемую выборку не менее 150 страниц.
3. Перед каждым сценарием фиксировать состояние cache.
4. Измерить полный wall-clock для 1, 2, 4 и 8 workers.
5. Добавить `duration_seconds` непосредственно в `omr_report.csv`.
6. Отдельно измерить page extraction, detector, preprocessing, Audiveris и MIDI.
7. Считать throughput `pages/hour` и parallel efficiency.
8. Повторить каждый worker-сценарий минимум три раза.
9. Привести median и диапазон batch time.
10. Проверить, не растёт ли failure rate при параллельном запуске.

Parallel efficiency:

```text
speedup(N) = time(1 worker) / time(N workers)

efficiency(N) = speedup(N) / N
```

## 10. Вывод

На текущей выборке успешный Audiveris OMR занимает в среднем 16,018 с на страницу, медиана равна 12,288 с, p95 — 29,031 с. Наблюдается длинный успешный выброс 131,707 с. Failed страницы в среднем завершаются быстрее, поскольку часть из них отклоняется на ранних этапах.

При сохранении текущей доли OMR-кандидатов идеальная обработка 87963 документов заняла бы около 828 дней одним worker или 103 дней восемью workers. Реальное время будет выше из-за неполного масштабирования, повторов, хранения и операционных пауз.

Главный bottleneck — CPU-bound Audiveris. Основные направления ускорения: уменьшение числа кандидатов, `skip-existing`, `resume`, ограниченный параллелизм, кэширование 300 DPI страниц и измерение внутренних шагов Audiveris. Перед проектированием промышленной инфраструктуры необходимо провести отдельный benchmark 1/2/4/8 workers с фиксацией hardware и полного wall-clock.
